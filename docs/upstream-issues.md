# Upstream issues

This file indexes every third-party limitation this repository works around, defers around, or compensates for. Each entry says why the problem matters here, what the repository carries because of it and exactly where that lives, the filed issue and its status, and the precise upstream change that lets the compensation be deleted.

It is an INDEX, not an archive. The full text of a filed report lives in the upstream issue; reproducing it here would give a reader two copies to keep in sync and no way to tell which one is current.

## How to work with this mechanism

Add the entry in the SAME change as the compensation. A compensation with no entry is a cleanup nobody will remember, and reconstructing the reasoning months later gets it wrong.

Re-check every Open entry whenever this repository's Hugo pin moves, which is the `hugo-version` inputs in `.github/workflows/ci.yml` (`0.164.0` by default, with floor rows at `0.160.0` and one row at `0.161.1`). A version bump is the moment to see whether a fix shipped; fixed-but-unreleased means keep waiting. An entry whose upstream is a CONVENTION rather than a dependency has no pin to watch; its re-check moment is any change to the version the repository consumes it at -- for the Agent Skills discovery draft, the `skills_index.schema` default in `modules/agent-readiness` and the v0.2.0 references in that module's README. Stamp what the re-check found into the entry with its date, because an entry whose claims carry no dates cannot be told apart from one nobody has looked at.

When upstream fixes an entry, do its **Remove when** action in full -- the code, the configuration, the documentation mentions and the tests -- then move the entry to `Resolved` with the fixing version. Re-verify against the real fix before deleting anything: a fix that changed shape in review can leave a gap the compensation was covering.

## Hugo

### `GetSortedMapValues` reads the map after releasing the read lock ([gohugoio/hugo#15237](https://github.com/gohugoio/hugo/issues/15237))

**Why:** `Scratch.GetSortedMapValues` in `common/hstore/scratch.go` takes the read lock, copies out the map header, releases the lock at line 141, and only then ranges the map at line 143 and indexes it at line 151. `SetInMap` writes into that same map under the write lock, and a mutex protects a map only while both sides hold it, so the accessor races a concurrent write exactly as an `index` or `range` on a map pulled out with `Get` does -- and the Go runtime aborts the process rather than tolerating it. Established by reading the source and by a standalone Go test that uses only the exported store API and fails on every run, landing at both unlocked accesses. Verified 2026-08-22: the file is byte-identical at `v0.164.0`, at `v0.165.0` (the latest release) and on `master`, so this is live rather than fixed-after-our-pin. It reaches templates because `hugo.Store`, `site.Store`, `PAGE.Store` and `SHORTCODE.Store` all return this type and Hugo renders pages concurrently; it matters here because `modules/url-retirement` collects registrations into store maps across pages and enumerates them when it renders its documents.

**Workaround:** `scripts/check-store-map-reads.sh` flags every `GetSortedMapValues` call and accepts one only where an adjacent Go-template comment carries `no-concurrent-writer:` followed by the reason no write to that key can be in flight there; the script also carries the known-answer self-test that proves that rule still works. Five calls carry such a marker: `modules/url-retirement/layouts/_partials/url-retirement/manifest/lines.html`, `manifest/redundant-extra.html`, `redirects/lines.html`, and two in `redirects/pagers.html`. The store paragraph in `CLAUDE.md` and the `WHICH PASS DECIDES` paragraph in `manifest/redundant-extra.html` both state the constraint in prose. No template was rewritten to avoid the accessor: no concurrent writer to those keys was found, so the compensation is the discipline that keeps it that way rather than a change in behavior.

**Remove when:** upstream holds the lock across the whole of `GetSortedMapValues` (or copies the map under it) AND this repository's Hugo pin has moved to a release carrying that fix, with the floor rows in `.github/workflows/ci.yml` moved too -- a floor row still running an older Hugo keeps the hazard live for that build. Re-verify first by rebuilding the Go reproduction from the upstream issue against the new version and watching it pass; a changelog line is evidence a fix shipped, not evidence this one did. Then delete, in one change: the `GetSortedMapValues` arm of `scripts/check-store-map-reads.sh` together with the five self-test cases that exercise it (`unmarked`, `marked-in-block`, `marker-as-output`, `marker-without-reason`, `marker-not-reused`), the five `no-concurrent-writer:` comments, the sentences about the accessor in `CLAUDE.md`, and the corresponding clause in `redundant-extra.html`. Everything the check says about `Get` STAYS: `Get` returns the live map whatever upstream does to the accessor, so its rules, its self-test cases and its prose remain correct.

**Investigated and deliberately not filed:** `Scratch.Add` in the same file performs a check-then-set that is not atomic -- it reads the existing value under the read lock, releases it, computes, and writes under the write lock -- so two concurrent `Add` calls on one key can lose an update. It was kept out of the filed report to leave that report to one defect with one reproduction, and nothing here depends on `Add`; this repository already prefers `SetInMap` for the collection case and says why in `lib/record-url.html`. File it separately if a module ever needs `Add` under concurrent rendering.

### `canonifyURLs` consumes a path segment that belongs to the page, not to the baseURL (`not filed`)

**Why:** with `canonifyURLs = true` Hugo rewrites root-relative URLs in HTML output into absolute ones after the templates have run, and to keep that rewrite from doubling the baseURL path it also makes the whole Page family stop emitting that path -- measured at v0.164.0 under `baseURL = 'https://example.org/docs/'`, a page's `.RelPermalink` comes back without the `/docs` prefix while its `.Permalink` keeps it. The rewrite then puts the path back by consuming a leading segment that matches it, and it cannot tell that segment from a CONTENT path that happens to begin the same way. For a page at content path `docs/inner` under that baseURL the two derivations disagree: `.Permalink` states `https://example.org/docs/docs/inner/`, which is where the file is served from, and the published `href` states `https://example.org/docs/inner/`, which resolves to no published file at all. Established with a standalone four-page probe site built twice at v0.164.0 with no module involved, comparing the plain-text render of `.RelPermalink` and `.Permalink` against the rewritten HTML and against the published tree; a control page outside the colliding section (`content/other.md`) is absolutized correctly in the same build, which is what isolates the collision to the shared segment. The setting is off by default and Hugo's own documentation calls it a legacy feature marked for removal and recommends against it.

**Workaround:** None, and none is needed for shipped code: no module in this repository emits a root-relative URL for the post-processor to rewrite -- every one of them states absolute URLs from `.Permalink` or `absURL`, which the pass leaves untouched, and the canonifyURLs build in each module's suite is what holds them to that. The compensation is confined to ONE test: `modules/copy-page/test/tests/04-subpath.spec.js` takes its "the setting is really on" control from the module's own script tag rather than from a page link, because that fixture's section is literally named `docs` under a baseURL path of `/docs` and its page links are therefore mangled by this behavior. The reason is stated at the assertion.

**Remove when:** Hugo distinguishes the baseURL path from a page path that shares its leading segment, so a page under a colliding section is absolutized to the URL its own `.Permalink` states. Re-verify by rebuilding the probe described above against the new version -- a colliding page and a non-colliding one in one build, comparing the rewritten `href` against `.Permalink` and against the published tree -- before changing anything. Then the only edit is to `04-subpath.spec.js`: the control may go back to a page link, and the paragraph explaining why it does not can go with it. Nothing else in the repository depends on this behavior either way.

**Not filed, deliberately:** the behavior is real and silent, but it is reachable only through a setting Hugo documents as legacy and recommends against, in the narrow case where a content section repeats the baseURL's last path segment, and nothing this repository ships is affected. Filing was weighed and deferred rather than dismissed; the evidence above is what a report would carry, so it can be filed as it stands if a consuming site ever meets this. File it through the upstream-issue-protocol if so -- rebuild the probe first, and search the tracker for existing `canonifyURLs` reports, which this entry has not done.

## Agent Skills discovery convention

### v0.2.0 leaves a multi-file skill no route but an archive nobody publishes (comment on [cloudflare/agent-skills-discovery-rfc#2](https://github.com/cloudflare/agent-skills-discovery-rfc/issues/2))

**Why:** the discovery draft (v0.2.0, Cloudflare-authored, read 2026-08-29 at the repository above) defines exactly two distribution types -- `skill-md`, a single file whose digest covers the `SKILL.md` bytes, and `archive`, a `.tar.gz` or `.zip` whose digest covers the archive bytes -- and specifies sibling loading only for archives. Real skills are multi-file (measured 2026-08-29 against github.com/anthropics/skills: eighteen of its twenty skills carry supporting files, and the repository publishes no releases at all) and skill developers publish them as files in a repository, not as archives, so a `skill-md` entry pointing at such a skill republishes a body whose relative references resolve to nothing, and no spec-conformant route exists that does not require somebody to build and host an archive. The draft's own history shows per-file listing was considered and dropped: v0.1.0 carried a `files` array, and the shipped v0.2.0 changelog replaced it and the `package` object with "a flat single-artifact model" (verbatim, re-read 2026-08-29). Issue #2 (jedisct1, 2026-01-21) asks for per-file objects with integrity metadata; the maintainer replied twice (2026-01-26 and 2026-02-13, verified against the issue's comment feed on 2026-08-29), agreeing "having an SRI-like hash here at the app-level makes sense" and pointing at a "v0.2.0 PR addressing this" -- PR #6, which proposed `files` as `{path, digest}[]`. That PR was superseded by PR #8 (jonathanhefner, merged 2026-03-23), whose body states "Replace the `files` array, per-file digests, skill-level digest computation, and `package` object with a simpler" single-artifact model; the review objections behind the removal concern archives as manifest subjects (UNIX permissions, symlinks and empty directories, unbounded file counts, and an archive smuggling files absent from the manifest), most of which do not arise for loose files a publisher serves directly. Issue #2 remains open, the shipped spec does not serve the per-file case, and the RFC is being adopted into the Agent Skills specification through agentskills/agentskills#254, where spec-detail discussion has moved. A substantiating comment carrying this repository's field data was posted on 2026-08-29: <https://github.com/cloudflare/agent-skills-discovery-rfc/issues/2#issuecomment-5462867834>.

**Workaround:** `modules/agent-readiness` extends the convention: a `skill-md` entry may declare a `files` list, each declared file is fetched from the source directory and republished beside the republished `SKILL.md`, and the index entry carries a non-standard `files` member (per-file `path`, `url` and `sha256` digest of the published copy). Safe under the draft's own "Clients MUST ignore unrecognized fields", and documented as an extension in `modules/agent-readiness/README.md` ("The `files` member is this module's extension of the convention"); the resolution lives in `layouts/_partials/agent-readiness/lib/skill-files.html` and the entry assembly in `layouts/_partials/agent-readiness/skills.html`, locked by `test/tests/04-skills.spec.js` and `modules/test-composition/tests/04-skill-artifacts.spec.js`.

**Remove when:** the convention itself defines a multi-file distribution shape for `skill-md` entries -- a spec'd per-file listing with digests, or whatever shape resolves issue #2 -- AND `skills_index.schema` can name a published version carrying it. Watch BOTH venues at every re-check: the Cloudflare repository (dormant since 2026-03-24) and agentskills/agentskills#254, the adoption pull request the discovery spec is moving into. Re-verify by validating the module's emitted index against that version's actual member names before touching anything, then rename or reshape the `files` member to the spec'd form in `skills.html`, update the README's extension paragraphs to cite the spec instead of disclaiming one, and retarget the suite assertions that pin the member's shape (`04-skills.spec.js`, `04-skill-artifacts.spec.js`). The republication mechanism itself STAYS whatever the spec does: fetching and serving the declared files is how the site publishes the skill at all, and only the index representation is the compensation.
