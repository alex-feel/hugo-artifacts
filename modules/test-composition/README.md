# Cross-module composition test suite

Node build-output assertions for the surfaces that `modules/seo`, `modules/agent-readiness`, `modules/search`, `modules/pwa`, `modules/og-image`, `modules/url-retirement`, `modules/images`, `modules/social-share`, `modules/carousel`, `shortcodes/callout` and `shortcodes/github-profile` share: the consuming site's single `[outputs]` table, the generated-image hook that lets one module compose the image another module publishes, and the URL registry every module that publishes a page-less URL contributes to. This directory is a test suite, not a Hugo module -- it ships no `layouts/`, no `assets/` and no `go.mod` of its own, and nothing imports it. Only [`fixture/`](fixture/) carries a `go.mod`, because a Hugo consumer site needs one.

## Why this suite exists

Each module is proven on its own by its own suite, against a fixture that imports that module alone. No single-module fixture can see what happens when a site imports several of them at once, and that is exactly where the modules interact.

The first shared surface is the output list:

- `[outputFormats]` and `[mediaTypes]` shipped in a module's `hugo.toml` merge ADDITIVELY into the consumer configuration. A site that imports `agent-readiness`, `search` and `url-retirement` can name `llmstxt`, `llmsindex`, `agentfacts`, `agentskills`, `searchindex`, `opensearch`, `redirects` and `urlmanifest` without defining any of them, and `redirects` carries the `[mediaTypes]` half of the same claim: its suffix-less media type is declared in a module and the consumer restates neither. `pwa` needs one more name in the same list, `webappmanifest`, and defines no `[outputFormats]` table for it because that format is one of Hugo's own -- so nothing in a module configuration announces it, and only this README and the suite's built-in list carry it. `og-image` defines no output format at all: it composes an image, and an image is not a document Hugo publishes per page kind.
- `[outputs]` does NOT. Hugo replaces the output list per page kind rather than merging it, and a module's own `[outputs]` table never reaches the consumer configuration at all, so every module README has to show an `[outputs]` block of its own.

A consumer who follows two of those READMEs literally lands in one of two states. Two `[outputs]` tables in one file is a hard configuration-load failure (`unmarshal failed: toml: table outputs already exists`), which is loud and self-correcting. One table replacing the other loads cleanly, exits 0, prints no warning -- and silently stops publishing every document the replaced list asked for. The second shape is what this suite catches.

The second shared surface is the publication answer. Several module documents publish NOTHING on purpose -- a Markdown twin withheld from an excluded page, an Agent Skills index withheld when no skill resolves -- and Hugo publishes no file for a template that renders no bytes while still reporting the format on the page with a resolving `.RelPermalink`, silently, at every log level. So `url-retirement`'s `/url-manifest.txt` asks the module that OWNS a format, through a partial that module ships at `layouts/_partials/url-retirement/publishes/<format>.html`, and the answer has to cross a module boundary to arrive. Neither module's own suite can show that: url-retirement's fixture ships its hooks itself, and agent-readiness's fixture publishes no manifest for an answer to correct.

The third shared surface is the generated social card. `[params.seo] image_partial` names a partial that composes an image for a page with no image of its own, and `og-image/card.html` is such a partial; neither module's own suite can show the two halves meeting. The og-image fixture composes cards and reads their pixels but publishes no tag to follow, and the seo fixture proves the hook against a deliberately minimal stand-in partial of its own -- which is what keeps that suite a test of the HOOK rather than of any one supplier, and is why the stand-in stays there instead of being swapped for the real module. So "a real generated card reached `og:image`" exists only here, and it is asserted from the published bytes: the file the tag names is opened, sniffed and decoded, because a URL in a tag says nothing about whether anything is at the other end of it.

The fourth shared surface is the URL registry. `/url-manifest.txt` is built by crossing pages with their output formats, so a URL belonging to no page is invisible to it however correct every hook is -- and modules publish such URLs constantly: a service worker, a page carrying `build.list = never`, an image resolved out of the consuming site's own bundle, a remote avatar copied at build time, an Agent Skills artifact republished under a name-keyed path. Each of those arrives by one of two mechanisms, and which one is decided by whether the publishing module can guarantee the render pass it runs in. Seven modules register what they publish; `agent-readiness` cannot, because its artifacts are copied by whichever caller first reaches a shared resolution, so it ANSWERS a question the manifest asks during its own pass. Both mechanisms cross a module boundary, so neither module's own suite can see either: url-retirement's fixture ships its hooks and registrations itself, and the publishing modules' fixtures publish no manifest for a URL to arrive in.

## What the three builds assert

| Assertion | What it holds |
| --- | --- |
| every module document is published side by side | `/llms.txt`, `/llms-index.txt`, `/about.md`, `/index.md`, `/searchindex.json`, `/opensearch.xml`, `/robots.txt`, `/manifest.webmanifest`, `/_redirects`, `/url-manifest.txt` and `/index.html` all exist, non-empty, out of ONE build |
| the merged home list carries every format the modules define | the list is checked against the `[outputFormats.*]` names read out of `modules/agent-readiness/hugo.toml`, `modules/search/hugo.toml` and `modules/url-retirement/hugo.toml`, plus the built-in names a replacing list drops (`html`, `rss`, `markdown`, and `webappmanifest` for `pwa`), so a module that adds a format a consumer must wire fails here until the fixture wires it |
| exactly one `[outputs]` table | the merged single table is the only shape that can hold every module the fixture imports |
| the twins describe the page the index holds | the agent-readiness `llms.txt` / `about.md` entries and the search index record name the same page |
| the seo head surface and the search body markup coexist | the seo module contributes head markup only, so its composition evidence is that its markup renders on the same page through the same `baseof.html` |
| ONE build stamp reaches every dated document | the twins' `build_time`, both link indexes' and `/about.md`'s `> Build time:` line, and the search index's `generated` field are one string, although two different modules write them |
| the search module reaches that stamp by DELEGATION | equality is not enough to prove it -- the fixture builds in under a second while the stamp's precision is one second, so a search module computing its own value would print the same string. A white-box probe reads both modules' `hugo.Store` keys: the search module's own must be EMPTY (it delegated) while agent-readiness's holds the value. Deleting the delegation changes no published byte and fails only here. It is also the one place the repository verifies that `templates.Exists` sees a partial mounted from a MODULE, which the whole soft-dependency design rests on |
| a composed card outranks the site banner | the fixture configures `[params.seo] image_partial` AND a `default_image`, which is the only shape in which the hook's rank is observable: with no default configured a hook ranked below one would still answer, and every "an `og:image` is present" assertion passes either way |
| the card is real, and it is this site's | the URL `og:image` names is opened: it exists, sniffs as a 1200x630 PNG, and its corner pixel equals the corner pixel of the fixture's own committed base raster -- so the card was composed on the backdrop THIS site configured, not on anything the module carries |
| the tag and the pixels describe the same page | of two blog posts whose `og:title` lengths differ, the longer title's card draws the strictly wider first ink band, both from the same left anchor. A generator drawing the wrong page's words, or the same words on every card, satisfies every assertion above and fails this one -- measured as an ink extent, so nothing reads a glyph or depends on a font's metrics |
| a RESOURCE crossed the hook, not a string naming one | `og:image:width`/`height` are 1200/630, `og:image:type` is `image/png`, and the JSON-LD `primaryImageOfPage` carries the same URL with the same dimensions. The seo module fabricates no dimensions for a bare string, so dimensioned structured data exists only because a real image resource came back through the hook |
| a page the generator declines keeps the site banner | `[params.ogcard]` routes the home page and the blog section and nothing else, so `/search/` reaches a generator that has no template for it. Declining is silent by contract, so the published evidence is what the page carries instead: the banner, and no card path in any tag or structured-data node |
| each carded page carries its own card | no two pages in this fixture draw identical text, so every card URL in the tree is distinct -- a generator memoizing across pages would otherwise publish one card everywhere and satisfy every assertion above |
| at the default canvas each card is published once | the seo module skips its `1200x630` crop for an image that already measures exactly that, so the composed card is the file `og:image` names. The published `og/` directory and the set of card URLs the documents name must be the SAME set -- an extra file is a duplicate nothing requests, a missing one is a tag pointing at nothing, and only the pair catches both. A `[params.ogcard]` canvas moved off `1200x630` still pays for both files, which is what the og-image README documents |
| the og-image README describes that pairing | the paragraph a reader wiring the two modules actually meets, held to what this build does: that the seo module skips the crop, that the default canvas therefore publishes once, and what moving off it costs. The row above catches the behavior drifting; this one catches the prose drifting away from it, which nothing else here can see |
| every URL the manifest lists is a file this build wrote | the manifest exists to be diffed against production, so a line no fetch can confirm weakens every conclusion that diff draws. Each listed URL is resolved to the file that serves it and opened |
| every module document the build serves is listed | the mirror of the assertion above, and the direction that fails silently: a wrong answer from any module's hook removes a URL production really serves, and the coverage check the manifest exists for stops seeing it. A short manifest is consistent with itself, so nothing in the tree comparison catches it |
| a page the twin renderer excludes keeps its own URL and loses its twin | `/search/` is listed and `/search/index.md` is not, because agent-readiness withholds that page's twin and Hugo writes no file for it -- while every page that DOES publish a twin keeps its line |
| a site-level document withheld for want of content is not listed either | `/.well-known/agent-skills/index.json` is wired on the home page and published by nothing, because this fixture configures no skills |
| a URL no page carries is listed because its publisher registered it | the manifest is built by crossing pages with their output formats, so a URL belonging to no page is invisible to it however correct every hook is. `/offline/` is a page carrying `build.list = never`, in no collection at all, and `/sw.js` is a Resource rather than a page; both are listed, and neither is in `sitemap.xml`, which is the page walk's own projection -- so nothing but a registration could have put them there |
| and a content-addressed URL is deliberately not | the pwa module publishes fingerprinted scripts beside the worker it registers, and none of them is listed: a hashed name changes with its own contents, so listing one would report a retirement and a new URL on every rebuild in the document whose only use is showing what really changed |
| the registrations come from the owning module, not from the fixture | white-box, because the manifest would look identical if the fixture had registered the two URLs itself: the calls live in `modules/pwa`'s own offline layout and service-worker partial, and no template in this fixture registers anything |
| the answers behind those omissions come from the owning modules | white-box, because the twin-omission and withheld-site-document assertions above would pass just as well if the fixture answered for those formats itself: the hook files live in `agent-readiness` and `search`, and the fixture ships no `_partials/url-retirement/` tree at all |
| a file a module published out of this site's own content is listed | four modules read the URL of a resource while rendering ordinary content, and reading it is what writes the file: a page-bundle raster through the `image` shortcode, a bundled SVG the seo module passes through uncropped, a global icon asset the callout resolves, and a share image. None is a Page, none is in `sitemap.xml`, and the site configured none of them for the registry |
| while every derivative they published is left out | the same modules publish resized rasters and composed cards under names carrying a hash of their own contents. The set is derived by walking the tree for `_hu_` names rather than listed here, so a new derivative cannot arrive unchecked, and not one of them may be listed |
| those registrations come from the owning modules | white-box, for the same reason as the pwa row above: the calls live in `seo`, `images`, `social-share`, `carousel`, `callout` and `github-profile`, each at the line where it reads a resource's URL, and no template in this fixture registers anything |
| a remote file a module copied at build time is listed | under `avatar="fetch"` the `github-profile` shortcode copies each avatar the origin-backed builds' canned data names, publishing it at a stable URL-derived name at the site root; the copies the tree holds and the avatar lines the manifest carries are the SAME set, an entry whose data names no avatar renders the placeholder and registers nothing, and the registration survives `manifest.output_formats = false`, because the copy is published inline in the html pass and is therefore always in time |
| while the offline build publishes and lists no copy at all | the base build's canned data names no avatar URL, so the module fetches nothing, publishes nothing, registers nothing, and warns about nothing -- the mirror direction, and the reason the seam's two canned files are held to differing ONLY in their avatar URLs |
| the artifacts of an output format are listed although no page carries them | the `skills` build configures two agent skills, one of them declaring a supporting file, so `agent-readiness` republishes three artifacts at name-keyed paths that no walk of `.Site.Pages` reaches: two `SKILL.md` bodies and one loose declared file beside the second. What the manifest lists and what the build wrote must be the SAME set -- more than one, because with a single artifact an answer that named a constant URL would satisfy any assertion about it, and of more than one SHAPE, because an answer projecting entry URLs alone would carry both bodies while silently dropping the declared file |
| and they are listed with the per-format URLs switched off too | the load-bearing one. `url_retirement.manifest.output_formats` decides whether the publication hook runs, and therefore whether a registration placed where the artifacts are copied would have been in time: measured at v0.164.0, in time on every build with the setting on and refused on every build with it off. The third build has it off and the artifacts are still listed, which every push design fails and the pull passes |
| the side-file hook lives in the module that owns the format | white-box: `layouts/_partials/url-retirement/writes/agentskills.html` is in `agent-readiness`, and the fixture ships no `_partials/url-retirement/` tree at all |
| the index really advertises a digest for the URL that was listed | why the artifact must be in the registry rather than merely on disk: the index is reachable by the page walk and carries a SHA-256 per artifact, so an artifact that vanished from production unnoticed leaves a verifiable-looking pointer at a 404. The digest is recomputed from the published bytes |
| a build with no skill configured lists no artifact at all | the `base` build's own coverage, and the direction a constant answer would pass: with nothing configured the module publishes no index and no artifact, and no `/.well-known/agent-skills/` URL may appear |
| the build log carries no `WARN`, `ERROR` or deprecation line | every module in the chain degrades by warning rather than failing, so a composition regression surfaces as an exit-0 build with a warning in it. This gate covers og-image at no extra cost, and it is a strong one for that module in particular, whose whole contract is to warn rather than fail |

`agentskills` is wired in the merged home list in every build and publishes a document in only two of them, which is why there are three. In the `base` build no skill is configured, so the format is wired while publishing nothing -- exactly the condition the publication answers exist for, and the reason `/url-manifest.txt` does not list it there. That is the only coverage of an unconfigured skills surface, so configuring a skill in the shared configuration would have deleted it.

The other two builds configure two skills each. Every `[[params.agent.skills]]` entry names a REMOTE source the module fetches at build time and has no local form, so those builds fetch -- from `serve-origin.mjs`, a static origin over the committed [`fixture-origin/`](fixture-origin/) corpus, listening on `127.0.0.1`. Serving the bytes ourselves keeps the suite off anybody else's endpoint: no outside URL can turn a pull request red, and the artifact the specs read is one this repository wrote. It costs those builds a `[security.http] urls` allow-list, because Hugo's default policy denies a loopback fetch outright; that block is a test-harness affordance in [`fixture/skills.toml`](fixture/skills.toml) and a consuming site fetching a real origin needs nothing like it. The same overlay flips the fixture's github-profile fetch seam (`fixture/layouts/_partials/github-profile/fetch.html`) to the canned data file whose avatar URLs point at that origin, so the fetch-mode avatar copies exist in exactly the builds that may fetch, while the base build's file names no avatar and keeps that build offline and silent. The module's own suite renders the fetch arm too, against an origin of its own, but imports github-profile alone -- so the copies' arrival in the `url-retirement` manifest is observable only here.

Several published artifacts here are not documents at all, and they are what the registration assertions are about. The cards land beside their source asset as content-addressed derivatives of `fixture/assets/og/card-base.png`, one per carded page -- the home page, the blog section, and each blog post -- while `/search/` and every taxonomy page publish `/img/site-banner.png` instead. The pwa module adds `/sw.js`, deliberately unhashed so a browser update check can find it, and fingerprinted registration and install bundles beside it. The origin-backed builds add the github-profile avatar copies at the site root, under names derived from the avatar URL rather than from the image bytes, which is what lets them be listed at all. `og-image` and `pwa` therefore add no name to the merged `[outputs] home` list for any of those, and the format assertions in `tests/01-composition.spec.js` and `tests/02-readme.spec.js` are untouched by them: those derive their required set from the `[outputFormats.*]` tables the modules define, and a Resource is in none.

That is also why this fixture calls `pwa/head.html` from its `baseof.html` although it needs no PWA of its own. Importing the module publishes its output format and its offline page, but the service worker is built by that partial and by nothing else -- so without the call `/sw.js` is never written, and the URL class the whole registration mechanism exists for goes unbuilt in the one place both modules are present.

## Running

```bash
bash modules/test-composition/run-tests.sh
```

or, on Windows:

```text
modules\test-composition\run-tests.cmd
```

Either script performs the pre-launch hugo process check, builds `fixture/` three times -- `base` with no skill configured, then `skills` and `one-url-per-page` against the fixture origin it starts and stops around them -- into `fixture/public/<name>/`, fails on any deprecation or error line in any of the three build logs, and then runs the specs against the published trees. The suite has no npm dependencies: `node --test`, `node:assert` and `node:zlib` are enough, so no `npm install` is needed in this directory. `node:zlib` covers the PNG inflate in [`tests/lib/raster.js`](tests/lib/raster.js), the reduced reader the card assertions decode published bytes with; a PNG shape other than the one Hugo emits for a filtered image fails loudly there rather than decoding into something plausible.

The fixture resolves every module through `fixture/hugo.work` plus a `replace` in `fixture/go.mod`, both pointing at the sibling module directories in this repository, so the suite always tests the working tree rather than a published tag. The origin's port is fixed at 1919 in four places that must stay in step -- `serve-origin.mjs`, both runners, `fixture/skills.toml` and `fixture/data/github-profile-fetch-origin.json` -- because a Hugo configuration file cannot learn a port at run time, and it sits below the ephemeral range an operating system draws outbound source ports from, so an unrelated connection cannot take it. The server gives up after fifteen minutes, so a hard-killed run cannot leak it. The `require` entries those replaces answer carry the placeholder pseudo-version, which is correct in a fixture and only in a fixture: the version is never fetched, because the `replace` resolves it locally.
